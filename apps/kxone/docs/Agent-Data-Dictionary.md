# CRM AI 分析数据字典与口径

数据源为当前 CRM SQLite 的全历史业务投影。快照采用明确字段允许清单；新增数据库列不会自动暴露给模型。模型读取 `describe_data` 后应以实际返回的表、字段、行数和缺失说明为准。

## 表与关联

| 表 | 业务含义 | 主要关联/限制 |
|---|---|---|
| `leads` | 当前线索资料、来源、阶段、责任周期、结果、金额 | `id` 为线索 ID；`customer_ref` 为匿名客户号；当前字段不能证明历史归属。 |
| `lead_followups` | 历史跟进内容和计划 | `lead_id → leads.id`；`sales_user_id` 是实际记录人，不是当前负责人。 |
| `lead_dispatch_records` | 分配与转派事件 | `lead_id`；`manager_user_id` 是操作者，`sales_user_id` 是接收目标。 |
| `lead_appointments` | 有效与历史预约 | `lead_id`；`status` 决定有效性，不能只判断“曾经有预约”。 |
| `lead_appointment_events` | 创建、改期、取消、交接等预约事件 | `appointment_id`、`lead_id`；创建人以创建事件为证据，缺失则未知。 |
| `closer_availability` | 谈单师排班、容量及例外 | 时间为绝对时刻，校区和工作日边界用上海时区。 |
| `lead_pool_records` | 公海进出和前负责人 | 保留实际操作者及发生时间，不把当前状态当完整历史。 |
| `lead_activity_records` | 资料、成交、退款及其他业务修改审计 | JSON 内容经过脱敏；不能用一次当前金额推导逐笔现金流水。 |
| `lead_reminder_records` | 业务提醒应发送/已发送记录 | `business_version` 与业务记录版本区分；旧版本取消提醒不能算当前待办。 |
| `crm_wecom_user_bindings` | 业务员工姓名、角色、部门、启用状态 | 只投影允许字段；用户名、密码哈希、会话版本等认证信息不属于分析字段。 |
| `channel_integrations`、`channel_integration_audits` | 广告接入状态和业务审计 | 不投影签名密钥、授权凭证或原始广告载荷。 |
| `group_robot_notifications` | 通知执行状态及重试 | 发送次数不等于线索数；按需要区分业务提醒和执行尝试。 |
| `wecom_card_tasks`、`wecom_callback_logs` | 旧卡片/回调的历史业务执行状态 | 仅历史分析，不恢复已停用的企微业务流程。 |
| `lead_deletion_events` | 删除/恢复业务事件 | 原始线索 ID、业务编号、操作者、原因和时间；不能凭当前是否存在倒推历史。 |
| `xiangwu_form_submissions` | 官网咨询表单业务信息 | 仅投影来源、咨询详情及业务页面路径；姓名、联系方式、原始载荷哈希和外部接入 ID 不暴露。 |
| `analysis_records` | 跨跟进、预约、流转的可检索文本索引 | 包含记录类型、原记录 ID、线索、操作者、阶段、事件、时间和脱敏文字。 |

联表前先确定粒度：一条线索对应多条跟进/预约/事件。金额先按线索去重或分表聚合再关联；不得在一对多连接后直接求和导致重复计费。

默认表排除已删除线索及其关联记录；带 `_history` 后缀的历史表包含可恢复删除数据，`leads_history.deleted_at` 标明删除时间。用户分析全部历史、删除或恢复时明确选用历史表并说明范围；当前待办始终排除已删除线索。检索工具默认当前记录，分析删除历史时使用历史表。历史记录仍需脱敏，不能因已删除就允许暴露身份。

## 派生字段与统计含义

- 时间原字段投影为 UTC 绝对时刻，附加 `_shanghai` 和 `_date_shanghai`。自然语言“今日/某日”按上海日期；录入、跟进、预约、成交发生时间不能混用。缺失/无法解析时间为未知，列入缺口。
- 金额附加 `_cents` 整数分字段，`net_deal_amount_cents` 表示成交额扣退款后的业务净额。展示人民币时除以 100；不能当作本月现金收入。
- `current_owner_started_at` / `current_owner_first_followup_at` 描述当前责任周期；`first_followup_at` 为生命周期首次跟进。`owner_first_followup_seconds` 与 `lifecycle_first_followup_seconds` 不互换，缺失或倒序时间不计零/负时长。
- `current_followup_eligible` 和 `current_followup_overdue` 遵循业务待办资格：终态、公海、待领取、有效预约排除；当前期限一条线索最多一项，归当前负责人。历史跟进计划用于历史质量，不能形成重复当前任务。
- `customer_ref` 为客户匿名编号；姓名、电话和微信原列不存在于快照，联系方式仅保留可达性字段。`excluded_fragments` 表示文本安全过滤排除片段，归纳必须说明覆盖缺口。
- `star_rating` 只接受 1–5 作为有效评级；零/空/其他非法历史值单独列未知，不能自动给历史记录猜测星级。

## 当前状态、人员与展示契约

`describe_data` 返回结构化枚举、字段语义、关联关系、指标定义及无法推断的事实。当前成交以 `leads.status = 'converted'` 为准；`business_stage = 'finished'` 也包含无效和关闭。非空 `result_status` 与主状态冲突时单列异常，不能以 OR 合并。`converted_at` 只用于成交发生日期分析：缺失日期不否定当前成交，历史残留日期不证明当前成交；日期缺失记录不能分配到某个期间。

业务人员字符串标识关联 `crm_wecom_user_bindings.wecom_userid`，不关联数字 `id` / `crm_user_id`。按字典列出的每个人员字段分别关联，使用 LEFT JOIN 保留 system、缺失及历史未匹配者；历史分析不能因人员当前停用而删除记录。当前负责人和实际操作人分别统计。

付款标记及成交、录入、修改日期既不能证明计入某月现金收入，也不能证明应排除该月；到账时间未知时保持未知。来源或人员的成交表现比较应报告样本量和窗口，小样本差异不能支持长期效果或因果结论。

表格/图表绑定结果的全部行；标题、人群、时间和单位必须一致。展示子集或变更金额单位需要先重新查询，不能把全量结果改名当作子集。检索 `from` / `to` 均含精确时间边界；仅日期按上海该日的开始或末尾解释，分页的 offset 与实际页一致。

## 必须说明的已知缺口

1. 无可信家庭主键时只能说“线索数”，不能自动声称独立家庭数或用共享手机号去重。
2. 无广告成本台账时不能计算广告 ROI；成交表现只能作为观察，不能当投放收益。
3. 付款状态、累计成交额/退款额不是逐笔现金流水；缺少实际付款/退款时间与流水时不能算期间现金收入。
4. 当前来源和负责人是现状；历史来源变更和历史责任贡献必须引用真实审计/流转记录，缺失不能倒推。
5. 预约有效性以状态和线索当前引用为准；交接中的旧邀约人不等于已领取的新负责人，历史创建人缺事件时未知。
6. 文本检索分页不能算已阅读全部；结果中匹配总数、已读数量、截断和安全排除均应披露。
7. 跟进中提到费用、课程或时间只能证明出现了该顾虑；没有对照与充分证据不能归因成“造成流失”。

分析结果存储时固定查询、脱敏后的绑定参数 `query_params`、数据时点、行数、覆盖和来源。绑定参数按执行顺序单独保存为 JSON；空数组表示本次未使用绑定参数，旧结果字段缺失或 null 表示未保存，不能据此猜测占位符取值。页面依据与 HTML/Excel 导出均显示同一组保存参数，不将其拼接为 SQL 执行。后续数据修复不会改变原结果；新一轮分析使用新快照并说明时间变化。
