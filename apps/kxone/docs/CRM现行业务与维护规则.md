# CRM 现行业务与维护规则

2026-09-21 修复、强化与升级版。与旧企微文档冲突时，以本文件和当前运行版本为准。

## 需求与权限

CRM 以账号密码登录。企微 OAuth、个人应用卡片派发与回调领取已停用；历史文档仅用于理解旧数据，不能作为重新启用依据。群机器人是独立通知功能，保持线上既有开关。

所有主管共同管理线索，可跨主管范围单条或批量分配/转派。目标必须为启用中的业务角色；同一负责人拒绝转派，不重置领取时间或截止时间。批量任一无效或版本冲突整批回滚，返回失败线索编号。谈单阶段只能转给有效谈单师。

手动录入来源必填，按来源 JSON 中的 25 项及顺序展示；既有线索保留原始来源，未改变历史来源时仍可编辑其他资料。不同名称在统计中分别展示，不自动合并历史数据。外部广告来源不套用手动枚举。姓名 1–64 字，电话或微信至少一项，支持座机；历史非法电话未改变时可修改其他资料，并提示待核对。付款状态、成交纠错、无效恢复继续使用原有流程。

跟进默认显示当前星级。未改星级不发送变更；显式值只能为 1–5，省略时保留已有有效评级。已领取线索有效跟进后进入跟进中。

## 账号与开发接口

JWT sub 是账号表不可变主键，auth_version 与数据库一致才能使用。权限、部门、启用状态实时取账号数据，查询失败拒绝访问。旧格式 JWT 失效。改密/重置/登录名/角色/部门/启用状态变化增加 auth_version，同时撤销 access 与 refresh。

账号更新提交 expected_version；过期返回 409，普通资料更新不携带密码哈希。前端刷新最多一次，会话失效保留返回地址；账号、客户资料、预约和视图冲突保留输入，用户刷新最新版本并核对后重新提交，不自动覆盖。

current_owner_started_at 和 current_owner_first_followup_at 表示当前责任周期；first_followup_at 继续表示生命周期首次跟进。领取和谈单交接开始新周期，转派待领取、公海清空当前周期。缺失可信时间或负时长不记作零。

## 统计口径

当前回访一条线索最多一项，来源为线索当前 NextFollowupDueAt，归属 CurrentOwnerUserID。仅有效私有线索计入；排除终态、公海、待领取及有效预约。截止时间早于当前时刻即逾期。“今日”以 Asia/Shanghai 零点到次日零点判断。

统计日期范围按线索录入日期筛选，不改变为跟进事件日期。列表、看板、工作台、提醒使用相同资格判断；历史跟进计划只用于历史质量分析。人员/日期/状态/排序在下钻时完整传递。

个人首跟时效和推荐响应评分采用当前责任周期；生命周期响应指标保留原 first_followup_at。无法计入的个人响应样本单独返回数量。

## 预约闭环（生产保持关闭）

预约以绝对时间存储，工时、日程和每日负载固定 Asia/Shanghai；浏览器所在时区不改变输入含义。SQLite 的预约、可用时间和提醒查询按绝对时刻比较，兼容既有东八区与 UTC 值，避免字符串比较漏判冲突或提前提醒。当前预约仅包含 pending_assignment/scheduled，取消或爽约后可重新预约。

转派保留预约 ID、时间、校区、谈单师，进入“待接收者领取”。所有主管可改期、调整谈单师或取消；旧邀约人失去旧归属权限；接收者可查看，领取后才可操作。领取事务同时更新线索、预约邀约人、版本、交接事件和提醒。主管也必须先完成领取才能到访交付，不能通过“我来跟进”跳过预约交接。

取消预约保留未完成的线索分配；终结预约的历史参与者不重写。创建人来自 created 事件，没有事件显示未知。到访交付清除当前预约引用，历史预约仍保留，开始谈单负责人周期。

预约变化推进预约版本，旧版本提醒失效；领取恢复新邀约人的预约提醒。取消、爽约和谈单转交重建当前版本普通跟进提醒。生产通知开关保持原值，本轮不启用自动外部发送。

## 保存视图与交互

每账号最多 20 个视图，达到上限仍可重命名、更新条件和删除。删除默认视图时，在同一事务清理默认引用并增加偏好版本。列表保持筛选、排序、返回位置；错误状态保留表单输入并提供重试或刷新版本入口。

## 迁移与历史修复

000026 新增账号 auth_version/account_version，默认 1；000027 新增可空当前责任周期字段。结构迁移不重写客户姓名、金额、来源或原始日志。

历史修复工具 cmd/tools/repair_owner_cycles 使用两步流程：

1. `repair-owner-cycles -db <数据库> -plan <清单.json>`：只生成字段差异、原始事件证据、业务版本和资料版本，不含客户电话或姓名。
2. 备份、审阅清单后，`repair-owner-cycles -db <数据库> -apply <清单.json>`：逐项重新核验证据、版本和前值；写入最小字段及审计，重复执行幂等。冲突项跳过并返回非零状态，必须重新生成清单后复核。

只修有证据的责任周期、首次跟进和错误状态，不推断电话、来源、星级、回访期限。提醒更新失败时该项整笔回滚。

## 验证与上线

沿用 Go/Vue、现有 CRM CI。Go 测试与 vet、前端单测/lint/token/build/资源预算、32 项界面和原有 13 项业务浏览器回归保留；新增会话、评级、筛选、预约和视图真实 API/SQLite 浏览器流程。所有写入测试使用临时数据库，生产验收只读。

统一 Go 1.25.13；CI Node 24.15.0。每批在线 SQLite 备份、独立迁移演练和独立 Linux 构建。第二批起用迁移后的副本、独立 Redis 和回环端口实际启动新版本→上一安全版本，验证健康和未登录拒绝访问，再切换生产。测试副本永不恢复覆盖生产。

release_state.py 区分已应用/待应用迁移，核对校验和、顺序、数据库完整性及开关。业务数量变化仅记录，不作为损坏条件。发布异常按统一处理回滚到安全版本；首批没有安全基线时关闭认证服务。验证实际运行二进制、资源散列、服务和公网健康；保留旧资源兼容已打开页面。

回滚只切应用与静态资源，不恢复整库。安全基线为 /opt/kxone/releases/20260921T034619Z，禁止回滚到更早的认证实现。

第三批的人工应急回滚目标为第二批 `/opt/kxone/releases/20260921T041148Z`。确认该目录存在 `SECURITY_BASELINE` 后，在服务器执行：

```bash
set -e
test -f /opt/kxone/releases/20260921T041148Z/SECURITY_BASELINE
ln -sfn /opt/kxone/releases/20260921T041148Z /opt/kxone/current.rollback
mv -Tf /opt/kxone/current.rollback /opt/kxone/current
systemctl restart kxone-server kxone-worker
systemctl is-active kxone-server kxone-worker
curl --fail --max-time 10 http://127.0.0.1:18081/health
curl --fail --max-time 15 https://crm.example.com/health
```

之后核对 systemd MainPID 对应的 `/proc/<PID>/exe`、公网静态入口、迁移/数据库完整性和功能开关，记录实际版本。若服务不能健康启动，停止认证服务并排查，不切回旧鉴权实现；不使用任何整库备份覆盖线上新增业务。历史修复若需纠正，必须另行生成带当前版本与证据的反向差异清单，不能直接还原旧数据库。
