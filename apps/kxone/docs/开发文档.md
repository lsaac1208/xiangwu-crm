# 开发文档：自研 CRM 对接企业微信线索卡片、派发、领取与跟进

> 历史企微方案：OAuth、个人应用卡片派发与回调领取已停用。现行业务、权限、接口和验收以 [CRM现行业务与维护规则](CRM现行业务与维护规则.md) 为准；本文件不作为重新启用旧流程的依据。

## 1. 技术目标

通过企业微信自建应用能力，为自研 CRM 增加线索通知与移动端操作入口，实现：

1. CRM 向主管推送企业微信线索卡片。
2. 主管通过卡片进入 CRM H5 分配页。
3. CRM 向销售推送企业微信领取卡片。
4. 销售点击卡片按钮后，企业微信回调 CRM。
5. CRM 根据回调完成领取动作。
6. CRM 更新主管卡片和销售卡片状态。
7. 销售通过企业微信 OAuth 进入 CRM H5 页面填写跟进。

## 2. 总体架构

```text
广告平台 / 表单 / 电话系统
        ↓
CRM 线索中心
        ↓
线索派发服务 Lead Dispatch Service
        ↓
企业微信集成服务 WeCom Integration Service
        ↓
企业微信自建应用
        ↓
主管 / 销售 企业微信客户端
        ↓
CRM H5 页面
```

建议拆分以下服务模块：

| 模块                | 说明                           |
| ----------------- | ---------------------------- |
| Lead Service      | 线索主数据、状态流转、归属关系              |
| Dispatch Service  | 主管分配、销售领取、SLA 规则             |
| WeCom Service     | access_token、消息发送、卡片更新、回调解密  |
| Auth Service      | 企业微信 OAuth、UserID 绑定、CRM 登录态 |
| Follow-up Service | 跟进记录、跟进状态、下次跟进时间             |
| Audit Log Service | 操作日志、回调日志、异常日志               |

## 3. 企业微信侧准备

### 3.1 创建自建应用

在企业微信管理后台创建自建应用，记录以下参数：

```text
CorpID
AgentID
Secret
Token
EncodingAESKey
```

### 3.2 配置应用可见范围

应用可见范围必须包含：

1. 所有主管。
2. 所有销售。
3. CRM 管理员，视需要配置。
4. 测试账号。

如果成员不在应用可见范围内，将无法收到应用消息或无法正确完成部分更新操作。

### 3.3 配置回调地址

配置企业微信应用回调地址：

```text
GET  /api/wecom/callback
POST /api/wecom/callback
```

GET 用于验证 URL 有效性。

POST 用于接收企业微信事件，包括模板卡片按钮点击事件。

### 3.4 配置可信域名

CRM H5 域名需要配置为企业微信应用可信域名。

示例：

```text
crm.example.com
```

H5 页面必须通过可信域名访问，否则企业微信 OAuth 可能无法正常跳转或获取成员身份。

## 5. 线索状态机

```text
new
 ↓
pending_dispatch
 ↓
assigned_pending_claim
 ↓
claimed
 ↓
following
 ↓
converted / invalid / closed
```

允许状态流转：

| 当前状态                   | 动作     | 下一状态                   |
| ---------------------- | ------ | ---------------------- |
| new                    | 创建派发任务 | pending_dispatch       |
| pending_dispatch       | 主管分配销售 | assigned_pending_claim |
| assigned_pending_claim | 销售领取   | claimed                |
| claimed                | 销售填写跟进 | following              |
| following              | 标记成交   | converted              |
| following              | 标记无效   | invalid                |
| assigned_pending_claim | 主管转派   | assigned_pending_claim |
| claimed                | 主管转派   | assigned_pending_claim |
| 任意非成交状态                | 管理员关闭  | closed                 |

## 6. CRM 内部接口设计

### 6.1 新线索创建后触发派发

```http
POST /api/leads/{lead_id}/dispatch/init
```

处理逻辑：

1. 查询线索详情。
2. 根据规则找到主管。
3. 线索状态更新为 `pending_dispatch`。
4. 调用企业微信服务发送主管卡片。
5. 保存卡片 `task_id`、`msgid`、`response_code`。

### 6.2 主管分配销售

```http
POST /api/leads/{lead_id}/assign
```

请求体：

```json
{
  "manager_userid": "zhangsan",
  "sales_userid": "lisi",
  "remark": "客户咨询企业服务套餐 A，优先联系"
}
```

处理逻辑：

1. 校验当前用户是否为主管。
2. 校验线索是否允许分配。
3. 校验销售是否在主管管理范围内。
4. 更新 `assigned_sales_userid`。
5. 更新 `assigned_at`。
6. 更新状态为 `assigned_pending_claim`。
7. 写入分配记录。
8. 更新主管卡片为“已分配，待销售领取”。
9. 发送销售领取卡片。

### 6.3 销售领取线索

```http
POST /api/leads/{lead_id}/claim
```

请求体：

```json
{
  "sales_userid": "lisi",
  "source": "wecom_card",
  "task_id": "lead_10001_sales_claim"
}
```

处理逻辑必须使用原子更新。

示例 SQL：

```sql
UPDATE leads
SET owner_userid = :sales_userid,
    claimed_at = NOW(),
    status = 'claimed',
    updated_at = NOW()
WHERE id = :lead_id
  AND assigned_sales_userid = :sales_userid
  AND status = 'assigned_pending_claim';
```

如果影响行数为 1，领取成功。

如果影响行数为 0，需要查询当前线索状态并返回对应错误：

| 当前情况       | 返回    |
| ---------- | ----- |
| 已被领取       | 线索已领取 |
| 已转派        | 线索已转派 |
| 点击人不是被分配销售 | 无权限领取 |
| 线索已关闭      | 线索已关闭 |

领取成功后：

1. 写入操作日志。
2. 更新销售卡片为“已领取”。
3. 更新主管卡片为“某某已领取”。
4. 可选发送群机器人播报。

### 6.4 提交跟进记录

```http
POST /api/leads/{lead_id}/followups
```

请求体：

```json
{
  "sales_userid": "lisi",
  "followup_result": "connected",
  "intention_level": "high",
  "remark": "客户有明确需求，约定下午 3 点电话沟通报价",
  "next_followup_at": "2026-06-16 15:00:00",
  "is_valid": true
}
```

处理逻辑：

1. 校验当前用户是否为线索负责人。
2. 新增跟进记录。
3. 如果是首次跟进，写入 `first_followup_at`。
4. 更新线索状态为 `following`。
5. 可选更新销售卡片状态。
6. 可选通知主管。

## 8. 企业微信回调处理

### 8.1 回调入口

```http
GET  /api/wecom/callback
POST /api/wecom/callback
```

### 8.2 GET 验证

处理企业微信 URL 验证请求。

流程：

1. 读取 `msg_signature`、`timestamp`、`nonce`、`echostr`。
2. 使用企业微信 SDK 解密。
3. 返回明文 `echostr`。

### 8.3 POST 接收事件

流程：

1. 接收企业微信加密 XML。
2. 使用企业微信 SDK 解密。
3. **幂等检查**：基于 `task_id + from_userid + event_key` 构造 Redis 幂等键，有效期 10 分钟。
4. 解析事件类型。
5. 识别模板卡片点击事件。
6. 根据 `EventKey` 分发业务逻辑。
7. 写入回调日志。
8. 返回 success。

#### 幂等实现

```javascript
async function handleWeComCallback(event) {
  const idempotent_key = `wecom:callback:${event.task_id}:${event.from_userid}:${event.event_key}`;
  
  const acquired = await redis.set(idempotent_key, '1', 'EX', 600, 'NX');
  
  if (!acquired) {
    // 重复回调，直接返回成功
    return { success: true, message: 'duplicate_callback' };
  }
  
  await saveCallbackLog(event);
  const result = await processEvent(event);
  
  return result;
}
```

### 8.4 事件分发

事件键设计：

| EventKey      | 说明       | 处理方法             |
| ------------- | -------- | ---------------- |
| ASSIGN_LEAD   | 主管点击分配线索 | 返回或跳转 CRM H5 分配页 |
| CLAIM_LEAD    | 销售点击领取   | 执行领取逻辑           |
| VIEW_LEAD     | 查看线索     | 跳转 CRM H5 详情页    |
| FOLLOWUP_LEAD | 填写跟进     | 跳转 CRM H5 跟进页    |
| MARK_INVALID  | 标记无效     | 可选功能             |

### 8.5 领取事件处理伪代码

```python
def handle_claim_lead_event(event):
    from_userid = event.from_userid
    task_id = event.task_id
    response_code = event.response_code

    lead_id = parse_lead_id(task_id)

    save_callback_log(event)

    lead = lead_repo.get(lead_id)

    if lead.status != "assigned_pending_claim":
        return build_fail_response("线索当前不可领取")

    if lead.assigned_sales_userid != from_userid:

    )

    if not success:
        return build_fail_response("线索状态已变化，请刷新查看")

    wecom_card_service.update_sales_card_claimed(lead_id)
    wecom_card_service.update_supervisor_card_claimed(lead_id)

    audit_log_service.record(

        action="claim"
    )

    return build_success_response("领取成功")
```

## 9. 卡片更新逻辑

### 9.1 状态分离原则

**CRM 状态（真实状态）**：
- 存储在 `leads` 表
- 所有业务判断以此为准
- 状态变更必须成功

**卡片状态（展示状态）**：
- 存储在 `wecom_card_tasks` 表
- 仅用于跟踪展示一致性
- 更新失败不回滚业务状态

### 9.2 更新主管卡片


### 9.4 response_code 生命周期管理

**规则**：
- 企业微信返回的 `response_code` 有效期约 1 小时
- 每次发送卡片时记录 `response_code_expire_at = NOW() + INTERVAL 50 MINUTE`
- 更新前检查是否过期，过期则重发新卡片

**更新逻辑**：

```javascript
async function updateCard(lead_id, new_content, card_scene) {
  const card_task = await getLatestCardTask(lead_id, card_scene);
  
  // 检查 response_code 是否过期
  if (card_task.response_code_expire_at < new Date()) {
    return await sendNewCard(lead_id, new_content, card_scene);
  }
  
  // 尝试更新
  const result = await wecom_api.updateCard({
    response_code: card_task.response_code,
    content: new_content
  });
  
  if (result.success) {
    await updateCardTaskStatus(card_task.id, 'updated');
  } else if (result.error === 'invalid_response_code') {
    // response_code 实际已失效，重发新卡片
    return await sendNewCard(lead_id, new_content, card_scene);
  } else {
    // 其他错误，标记失败，等待补偿任务重试
    await updateCardTaskStatus(card_task.id, 'update_failed', {
      last_error: result.error,
      next_retry_at: new Date(Date.now() + 60000)  // 1分钟后重试
    });
  }
}
```

### 9.5 补偿任务（定时执行）

**任务频率**：每 5 分钟

**筛选条件**：
```sql
SELECT * FROM wecom_card_tasks
WHERE card_status IN ('update_failed', 'expired')
  AND retry_count < 3
  AND (next_retry_at IS NULL OR next_retry_at <= NOW())
ORDER BY next_retry_at ASC
LIMIT 100;
```

**处理逻辑**：
1. 检查 `response_code` 是否过期
2. 过期 → 发送新卡片，旧卡片标记 `replaced`
3. 未过期 → 重试更新，`retry_count + 1`
4. 3 次仍失败 → 发送新卡片

## 10. CRM H5 企业微信身份识别

### 10.1 使用场景

以下页面需要识别当前企业微信成员身份：

1. 主管分配页。
2. 线索详情页。
3. 销售跟进页。
4. 销售领取后的查看页。

### 10.2 登录流程

```text
用户从企业微信卡片点击 H5 链接
        ↓
CRM 前端检查 localStorage 是否有 access_token
        ↓
无 token 或 token 过期 → 重定向到企业微信 OAuth
        ↓
企业微信回调 /api/auth/wecom/callback?code=xxx
        ↓
CRM 后端用 code 换取 UserID
        ↓
查询 crm_wecom_user_bindings 表获取 crm_user_id
        ↓
生成 JWT：{ user_id, wecom_userid, role, exp }
        ↓
返回前端：{ access_token, refresh_token, expires_in }
        ↓
前端存储 token，跳转到原目标页面
```

### 10.3 Token 设计

**Access Token（短期）**：
- 有效期：2 小时
- 存储：前端 localStorage
- 用于：所有 API 请求的 Authorization header

**Refresh Token（长期）**：
- 有效期：7 天
- 存储：前端 localStorage + 后端 Redis
- 用于：access_token 过期后自动刷新

**JWT Payload**：
```json
{
  "user_id": 123,
  "wecom_userid": "zhangsan",
  "role": "sales",
  "department_id": 10,
  "iat": 1687766400,
  "exp": 1687773600
}
```

### 10.4 Token 刷新机制

前端 axios 拦截器：

```javascript
axios.interceptors.response.use(
  response => response,
  async error => {
    if (error.response.status === 401) {
      const newToken = await refreshAccessToken();
      if (newToken) {
        error.config.headers.Authorization = `Bearer ${newToken}`;
        return axios.request(error.config);
      } else {
        redirectToWeComOAuth();
      }
    }
    return Promise.reject(error);
  }
);
```

## 11. 幂等设计

### 11.1 回调幂等

企业微信回调可能重复到达，需要通过以下字段做幂等：

```text
event_id
task_id
from_userid
event_key
lead_id
```

建议规则：

1. 相同 `task_id + from_userid + event_key` 在短时间内只处理一次。
2. 领取动作以数据库原子更新为最终幂等保障。
3. 回调日志必须完整保存，便于排查问题。

### 11.2 分配幂等

主管重复提交分配时：

1. 如果销售相同，不重复发送销售卡片。
2. 如果销售不同，视为转派。
3. 转派必须写入分配记录。
4. 原销售卡片需要更新或补发“线索已转派”通知。

### 11.3 卡片更新幂等

卡片更新失败不能回滚 CRM 主状态。

建议：

```text
CRM 状态更新成功
        ↓
尝试更新卡片
        ↓
更新成功：记录 card_status
更新失败：记录失败日志，补发新卡片
```

## 12. 安全设计

1. 企业微信回调必须校验签名并解密。
2. H5 页面必须通过企业微信 OAuth 获取当前 UserID。
3. 所有线索接口必须校验 CRM 登录态。
4. 主管只能操作自己负责范围内的线索。
5. 销售只能查看和操作分配给自己的线索。
6. 手机号在企业微信卡片中默认脱敏。
7. 原始手机号仅在 CRM 权限允许时展示。
8. 企业微信 Secret、Token、EncodingAESKey 必须加密存储。
9. access_token 需要缓存，避免频繁请求。
10. 所有状态变更必须写操作日志。

## 13. 定时任务设计

### 13.1 主管未分配提醒任务

任务频率：

```text
每 1 分钟执行一次
```

筛选条件：

```sql
status = 'pending_dispatch'
AND created_at <= NOW() - INTERVAL 3 MINUTE
```

处理：

1. 给主管发送提醒卡片或文本提醒。
2. 记录提醒次数。
3. 超过阈值通知上级主管。

### 13.2 销售未领取提醒任务

筛选条件：

```sql
status = 'assigned_pending_claim'
AND assigned_at <= NOW() - INTERVAL 3 MINUTE
```

处理：

1. 给销售发送提醒。
2. 超过 5 分钟同时提醒主管。
3. 超过 10 分钟允许主管转派。

## 15. 测试用例
